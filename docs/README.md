# 文档地图（什么内容放哪里）

> 一条规矩：**文档按「读者」和「寿命」分家**。放错地方比不写更糟——看的人找不到，
> 写的人以为有人看。仓库里出现过两类具体事故：README 里堆了 320 行开发日志（读者是使用者，
> 却要翻完"已完成清单"才知道怎么装），以及**同一件事写了两套判据**（清理按名字、复用按身份）。

## 放哪儿

| 位置 | 放什么 | 寿命 | 读者 |
|---|---|---|---|
| [`../README.md`](../README.md) | **介绍这个插件**：它能做什么、怎么装、怎么用、出问题先看哪 | 常驻 | **使用者** |
| [`开发须知.md`](./开发须知.md) | 改代码前必须知道的：AI 协作纪律、热重载与审批策略的**实测结论** | 常驻 | 贡献者 |
| [`审查报告/`](./审查报告/) | **某一时点**的审查结论（文档×实现对齐、立项审查） | **快照，会过时** | 审查者、追账的人 |
| `立项.md`（**不入库**，见 `.gitignore`） | 需求正文 + **批次决策台账**：每一批做了什么、踩了什么坑、下一步 | 常驻 | 项目主 |
| `git log` | 逐次改动与理由（提交按主题分组） | 永久 | 所有人 |

## 新内容该写哪儿

1. **"怎么做"给使用者看** → `README.md`；**"为什么这么改、当时踩了什么坑"** → `立项.md` 台账或提交信息，
   **不要写进 README**（README 是介绍页，不是复盘页）。
2. **一次性的结论**（"某天查到 X 与 Y 不一致"）→ `审查报告/`，并在开头写明**日期与依据**，
   让人一眼知道它会过时；不要与常驻须知混在一起。
3. **改代码的人必须遵守的规矩** → `开发须知.md`。
4. **文档里的数字必须能被复核，且只能有一个来源**。已经栽过两次：
   README 写"43 个测试"（实际 455）、探针写死"29 个工具"（实际 33）——
   两处都让**看的人以为插件坏了**。计数类断言一律从插件自己的声明读（如 `TOOL_NAMES`）。
5. **文档引用的路径必须真的存在**。同一类事故：README 指向 `立项.md`（已不入库 ⇒ GitHub 上是死链）、
   写着作者本机的 `C:\Users\...\profiles\web`。**对外部读者无效的具体路径不许出现在 README**。
